# marked 18.1.3 for formatted messages in the app

The app shows thread messages, whose text is standard markdown, as formatting. It uses only marked's lexer
(`mobile/src/markdown.ts`) and renders the tokens itself as React Native text, so marked never produces HTML and the
app never renders any.

18.1.3 is the latest stable release. The package has no dependencies, and its `lib/marked.esm.js` has no `require`,
no `import` and no Node built-in.

## marked none → 18.1.3

Source: https://github.com/markedjs/marked/releases (v18.0.0 through v18.1.3), and `lib/marked.esm.js` for what the lexer needs at runtime

- the lexer reads GFM paragraphs, headings, bold, italic, strikethrough, inline and fenced code, lists with a nested level and task items, blockquotes, rules and tables into tokens · test: mobile/src/markdown.test.ts
- a link's destination comes back as written, balanced parentheses included, and bare web and email addresses become links, so the app's scheme allowlist judges the real target · test: mobile/src/markdown.test.ts
- raw HTML and images come back as their own tokens: a block of HTML as one token, which the app shows as written, inline tags as tokens of their own with markdown lexed between them, and an image as a token the app shows as a link to it, never loading anything · test: mobile/src/markdown.test.ts
- numeric character references come back decoded in most text, with any other `&` then escaped as `&amp;` (18.1.1), while text inside `<pre>`, `<code>`, `<kbd>` and `<script>`, named references, code, raw HTML tags and link destinations come back as written, and an autolink is flagged literal; the app decodes numeric references and the five XML named ones in all text outside a block of HTML, between inline HTML tags too, and in a non-autolink destination, and shows any other named reference as written · test: mobile/src/markdown.test.ts
- in a loose task list the checkbox token sits inside the item's paragraph, and in a tight one beside it · test: mobile/src/markdown.test.ts
- the lexer uses RegExp named groups, Unicode property escapes and a lookbehind it feature-detects, and private class methods, which Metro's Hermes profile transpiles · not covered: the suite runs on Bun, with no Hermes; checked once by running the bundled parser on the Hermes 0.13 VM with marked's regular expressions left native (output identical to Bun's and Node's over 21 messages), and by `npx expo export --platform android`, whose hermesc 1.0.0 compiled the bundle
- the lexer turns `\r\n` and a lone `\r` into `\n` before anything else (`src/Lexer.ts` line 100, `carriageReturn` in `src/rules.ts` line 97), so the app applies the same rule once and hands that text to both its cost budget and the lexer · test: mobile/src/markdown.test.ts
- 18.1.0 and 18.1.3 remove cubic backtracking on a link destination and a quadratic scan for unmatched emphasis, but the lexer is still superlinear on nested emphasis, wide tables, a list item followed by many lines, deep container nesting, a long run of address characters before an `@` and a long delimiter run, so the app does not lex a message past 5,000 characters, 400 lines, a 1,000-character word or a 16-character run of leading container markers, and shows it, like nesting past eight levels, as plain text with its markers stripped in one linear pass; under those limits the costliest input measured, nested emphasis in one 5,000-character paragraph, took 1.6 to 2.0 s on the Hermes 0.13 VM, which is accepted · test: mobile/src/markdown.test.ts
