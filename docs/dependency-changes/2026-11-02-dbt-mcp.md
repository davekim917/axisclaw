# dbt-mcp 2.10.0 in the agent image

dbt-mcp 2.5.0 stopped starting once uv resolved pydantic 2.14.1 for it: `dbt_mcp/proxy/tools.py` imports the private
`pydantic._internal._typing_extra.eval_type_backport`, which pydantic 2.14 removed, so every call to the server failed
with an `ImportError` before any tool loaded. The Dockerfile pins only dbt-mcp, and uv resolves its dependencies
fresh on each build, so the gate never saw pydantic move. dbt-mcp 2.7.0 dropped the private import; 2.10.0 is the
latest stable. pydantic 2.14.2 does not restore the symbol, so pinning pydantic forward would not have helped, and
pinning it back to 2.13 would freeze a dependency the gate cannot see.

The install step now imports `dbt_mcp.main` after installing, so the next dependency that breaks the import fails
the image build instead of shipping a server that cannot start.

## docker:dbt-mcp 2.5.0 → 2.10.0

Source: https://github.com/dbt-labs/dbt-mcp/blob/main/CHANGELOG.md (v2.6.0, v2.7.0, v2.8.0, v2.9.0 and v2.10.0 sections)

- 2.7.0: the startup `ImportError` under pydantic 2.14 is fixed by removing the private `eval_type_backport` import; under 2.10.0 with pydantic 2.14.2 the server imports, answers `initialize` and lists its tools over stdio · not covered: an image build property, checked by the `import dbt_mcp.main` step in the Dockerfile itself
- 2.7.0: Admin, Discovery and Semantic Layer collection tools return bounded pages wrapped in `result` and `pagination` fields, and a caller must follow the continuation metadata for more; no host code parses the output, so the dbt-mcp capability text now tells the agent to follow `pagination` · test: src/capabilities.test.ts
- 2.7.0: optional host-injected response budgets and memory budgets, unlimited by default · not covered: the spawn sets none, so the defaults apply
- 2.8.0: tools declare their inputs and reject extra ones before running; one registry replaces the single- and multi-project tool sets; job and run ids carry ownership metadata for a hosting MCP to check · not covered: the local stdio server the spawn runs declares that metadata but enforces nothing with it, and input validation is tool behaviour the agent sees at call time
- 2.8.0: `list_jobs` requires a project or selected environment, and 2.10.0 makes the project optional again and restores account-wide listing when none is configured · not covered: tool behaviour against dbt Cloud
- 2.8.0: `AdminApiConfig.environment_id` replaces `prod_environment_id` internally; the `DBT_PROD_ENV_ID` setting the spawn passes is still read (checked in 2.10.0's `config/settings.py`) · not covered: verified by reading the settings model, and by the server starting with the spawn's variables
- 2.8.0: Flight SQL prepare calls time out after 60 seconds, and `query_metrics` falls back to the Semantic Layer GraphQL API · not covered: tool behaviour against dbt Cloud
- 2.10.0: `trigger_job_run`, `cancel_job_run` and `retry_job_run` accept environment-scoped write grants · not covered: the spawn disables all three by default through `DISABLE_TOOLS`, and their names are unchanged
- 2.9.0: new read-only tool `search_public_mesh_models`, registered only for multi-project configurations; the spawn configures one project, and 2.10.0's tool list differs from 2.5.0's by this name alone · not covered: read-only, and the spawn's `DISABLE_TOOLS` default names only the three job-mutating tools, whose names are unchanged in 2.10.0
- 2.9.0: dbt CLI and dbt-codegen calls run off the event loop and are killed on timeout; the `show` row limit and `get_column_lineage` casing are fixed · not covered: the spawn disables the dbt CLI and LSP toolsets
- 2.9.0: replaces the private `mcp.shared._httpx_utils` import with its own HTTP client factory for remote MCP connections · not covered: internal to dbt-mcp; the factory builds a default `httpx.AsyncClient`, which still reads the container's proxy environment
- 2.9.0: Python 3.14 support · not covered: the image installs dbt-mcp under uv's Python 3.12, unchanged
- 2.6.0: OAuth re-authentication hints, relative `DBT_PROJECT_DIR`/`DBT_PROFILES_DIR`/`DBT_PATH` resolution, and 10 seconds of clock skew for OAuth tokens · not covered: the spawn authenticates with a static token and sets none of those paths
- 2.10.0 widens its PyJWT range from `<2.14` to `<2.16`, so the image now resolves PyJWT 2.15.x where it had 2.13.x · not covered: PyJWT only verifies dbt Platform OAuth tokens, and the spawn authenticates with a static token
- security: urllib3 2.8.0 and PyJWT 2.15.0 (2.6.0), certifi 2026.7.22 (2.9.0) and 2026.10.19, which drops the emSign roots (2.10.0), are bumps in dbt-mcp's own lockfile · not covered: `uv tool install` does not read that lockfile and resolves the newest releases the declared ranges allow at build, PyJWT's widened range above included
